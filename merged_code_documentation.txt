COOLFluiD Merged Code Documentation
------------------------------------------------------


This folder is a clean source-oriented copy of the merged COOLFluiD codebase. It is intended for sharing with developers who need to understand what was merged, why it was merged this way, and where to inspect the changes made.


Merge Logic
----------------

The merge logic was simple: keep the newer merged COOLFluiD base as the main trunk, then bring the useful FR/RANS/transition capability forward without rewriting unrelated infrastructure.

1. Keep the merged framework and shared solver infrastructure as the baseline.

2. Preserve the original FR implementation (available on main andrea lani branch = baseline version) where it already works, especially for Navier-Stokes, turbulence, wall boundary conditions, high-order output, implicit Newton/PETSc execution, and transition source terms.

3. Avoid broad rewrites. 

4. Prefer explicit, inspectable case-file changes over hidden behavior. Old settings were generally kept commented near the active replacement so a developer can see what changed and why.

5. Build folders, dependencies, libraries, and temporary work files are not part of this clean copy.


What "VS" Means In This Work
----------------------------

The suffix "VS" is used as a marker for variant files and classes that distinguish this codebase from the older baseline version.

In this work, the VS path is mainly used to identify:

1. Physicality/positivity variants based on the more accurate Zhang-Shu post-update limiting lineage.

2. Variable-set-aware variants that are meant to work cleanly with the primitive/update variables used by the FR RANS and transition cases.

3. Test cases that should be compared against the original/non-VS case without hiding which path is being exercised.

The goal was not to rename the whole solver. The goal was to make the changed path visible. When a developer sees a VS case or class, they should treat it as part of the explicitly selected workflow.



Vatsalya Comments
-----------------

Search for "Vatsalya" in VS Code to find the intentionally documented changes.

The comments use normal file-appropriate syntax:

1. C++ source files use "//Vatsalya".

2. CFcase and text-style configuration files use "#Vatsalya" where applicable.

These comments were added so developers can quickly locate the important changes without reconstructing the whole debugging history. They usually appear above a commented old block or above the active replacement block and explain:

1. what old setting/code was kept for reference.

2. why it was not safe or sufficient for the workflow.

3. why the active replacement was used.

Recommended review method:

1. Open the clean repository in VS Code.

2. Search the whole folder for:

   Vatsalya

3. Review each comment in context before delivering, rebasing, or removing the explanatory comments.
